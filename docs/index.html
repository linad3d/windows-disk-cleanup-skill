A full disk is a data-loss event, not a chore

A Windows volume that reaches zero free bytes does not fail loudly — it silently corrupts whatever was mid-write.

In the incident this project was built from, a full C: drive truncated Chrome's History SQLite database into an empty shell. Chrome kept running and recorded nothing until it was restarted; the loss was discovered days later and the pre-incident history was unrecoverable locally.

That is why this toolkit optimizes for not destroying anything first, and for making the recovered space permanent second. Deletion is restricted to a hard-coded allowlist of known-regenerable cache paths — it cannot be pointed at an arbitrary directory. That is a structural property, not a policy you have to trust.

The hard part is subdirectory granularity

Most guides say to empty %TEMP%. The real space — and the real risk — is inside application data directories, where disposable cache sits next to your login session.

Inside one Chromium app profileVerdictWhy
Service Worker\CacheStorageDeleteOften >1.5 GB per profile; refetched on demand
Service Worker\DatabaseKeepWorker registrations; breaks offline features
Cache\Cache_Data, Code Cache, GPUCacheDeleteHTTP, bytecode and shader caches; rebuilt
Local Storage, CookiesKeepLogin tokens — deleting logs the user out
IndexedDBKeepApp state and local drafts

Deleting the parent folder to "clear the cache" is the common mistake. The project ships a per-application atlas of exactly these distinctions, covering chat clients, game engines, GPU drivers, developer toolchains, AI agents, and Windows itself.

Relocation that is safe to interrupt

Anything a human created or accumulated gets moved, never deleted — and only after a byte-level verification proves the copy is intact.

  1. Probe for locksRename the directory in place. Success means nothing holds a handle; failure means stop rather than force.
  2. Copyrobocopy /E /COPY:DAT /DCOPY:DAT. Remember exit codes below 8 are success.
  3. Recount independentlyTotal bytes and file count on both sides must match exactly. Do not trust the copy tool's own summary.
  4. Delete the sourceOnly now. Until this step the original is fully intact, which is what makes the operation abandonable at any earlier moment.
  5. Create the junctionmklink /J. Applications open a junction as a real directory — no app support needed.
  6. Confirm live writesStart the app and verify new files appear on the destination. A silently failed junction looks identical to a working one until you check.

Or run the scripts without Claude

.\Scan-DiskUsage.ps1 -Path C:\ -MinGB 0.3          # see what is actually big
.\Invoke-SafeClean.ps1                             # preview - deletes nothing
.\Invoke-SafeClean.ps1 -Category GPU,DevTools -Execute
.\Move-AppData.ps1 -Source "$env:APPDATA\SomeApp" -Destination "D:\AppData\SomeApp"
.\Test-Migration.ps1 -Watch "D:\AppData\SomeApp"    # prove the redirect is live

Frequently asked questions

Will cleaning app caches delete my chat history?
No, if you delete at the right granularity. In Chromium-based desktop apps the disposable items are Cache\Cache_Data, Code Cache, GPUCache, the shader caches, and Service Worker\CacheStorage. Login state lives in Local Storage, Cookies and persistent storage databases; application data lives in IndexedDB and Service Worker\Database. Deleting the whole profile folder to clear a cache is the common mistake.
Can I move the Feishu / Lark cache to another drive?
Yes, but not through the client's settings. Feishu's Settings offers only a "File save location" option, which controls the download directory rather than the cache. The data directory %APPDATA%\LarkShell must be relocated with an NTFS junction. In a verified run this freed 10.6 GB; the client retained its login session and wrote all new data to the target drive after restart.
Does robocopy exit code 1 mean the copy failed?
No. robocopy exit codes are a bit field, not a boolean. 0 means nothing needed copying, 1 means files were copied successfully, and 8 is the first code indicating a real failure. Testing $? or $LASTEXITCODE -ne 0 reports a perfectly good copy as a failure — test $LASTEXITCODE -lt 8.
Is it safe to delete the Unreal Engine DerivedDataCache?
Yes. Epic's documentation states DDC contents are disposable and regenerated from .uasset files. Relocating is still preferable, since deleting means recompiling shaders. UE 5.4+ uses Zen Store as the local DDC by default, so relocating %LOCALAPPDATA%\UnrealEngine\Common covers both in one move — stop zenserver.exe first.
Why does my PowerShell script fail with null-reference errors on valid lines?
Windows PowerShell 5.1 reads a UTF-8 file without a byte order mark as ANSI. Non-ASCII characters in comments corrupt the byte stream and can swallow adjacent statements, so variables silently become $null and the script half-runs without erroring. Keep helper .ps1 files pure ASCII, or save as UTF-8 with BOM.
Are NTFS junctions safe for application data?
Yes, within limits. A junction is a filesystem-level redirect resolved below the application layer, so applications open it as an ordinary directory. It requires NTFS on both sides and the same machine: never point one at a network share, a non-NTFS volume, or a removable drive that may be absent at boot, and never junction a directory the OS needs before all volumes mount.
How much space can this actually recover?
In the documented case study on a 299 GB system drive, a single session recovered 43.7 GB, taking free space from 19.0 GB to 62.7 GB. Roughly half was deleted regenerable cache and half was relocated, so the relocated portion cannot grow back on C:. The largest items were 17.4 GB of AI agent session transcripts, 10.6 GB of chat client data, and 7.4 GB of abandoned installer unpack directories.
Why does a full disk corrupt applications?
Writes in progress fail partway, and SQLite databases are especially vulnerable. In the incident behind this project, a full C: drive truncated Chrome's History database into an empty shell and Chrome kept running without recording anything until restarted. Treat a nearly full disk as an active data-loss risk.

中文说明

一个 Claude Code 技能 + 独立可用的 PowerShell 工具包：把爆满的 Windows C 盘救回来， 且不丢任何用户数据。

Windows 分区写到零字节时不会体面地报错，它会静默损坏当时正在写入的东西。 催生这个项目的那次事故里，写满的 C 盘把 Chrome 的 History 库截断成空壳， 而 Chrome 不重启就一直不再记录历史，几天后才被发现。

所以它的第一目标是不毁掉任何东西：删除只在写死的白名单内进行，无法被指向任意目录； 默认干跑，不加 -Execute 什么都不删；凡是人创造或积累的东西一律搬移而非删除， 且删源之前必须通过字节级重新计数校验。

真正难的不是清 %TEMP%，而是判断一个应用的哪个子目录可以扔—— 比如 Chromium 系应用里 Service Worker\CacheStorage 能删（单 profile 常超 1.5 GB），但旁边的 Service Worker\Database 不能，Local Storage 里还存着登录令牌。按文件夹一刀切的结果就是把自己登出。项目附带一份逐应用的缓存图谱， 覆盖飞书、微信、企业微信、虚幻引擎、NVIDIA、各类包管理器与 Windows 自身。

实测结果：299 GB 系统盘单次释放 43.7 GB（可用 19.0 GB → 62.7 GB），零数据丢失。
